# 整机迁移备份与一键还原：需求

## Summary

Rainote 应用内新增整机迁移备份：一键将全库数据 + 用户文件目录打包为可下载的备份包，并支持在新环境上传备份包一键还原（全量替换）。界面挂载现有"数据备份"按钮（当前指向不存在的端点，404 空壳），同步提供 agent 命令。目标是换电脑或本地损坏后，用户数据可恢复至最近一次备份时点、分钟级完成恢复。

## Problem Frame

应用目前的数据保护存在断层：服务器侧每日 mysqldump cron 只备数据库不含上传文件，且属于部署运维手段——用户在应用内无任何自助备份入口。界面上虽有一个"数据备份"按钮（ActionButtons.vue 调用 `GET /system/note/dataBak`），但后端端点不存在，点击即 404。用户文件（附件、头像、Excel 导入的图片）散落在 `ruoyi.profile` 目录树中，与数据库分开存放，单备任何一个都无法完整迁移。电脑损坏场景下，用户需要的是"装好应用 → 传一个包 → 一切如初"。文件层保护完全依赖手动触发，丢失窗口取决于用户的备份纪律——损坏时点与最后一次手动备份之间的差距即文件层丢失范围（数据库层另有服务器 cron 每日 dump 兜底）。

## Requirements

**备份（打包下载）**

- R1. 界面"数据备份"按钮触发备份：后端生成备份包并以文件流返回下载（无需用户去服务器目录找文件）。
- R2. 备份包内容：全库所有表的完整数据（结构+数据，JDBC 逻辑导出，不依赖 mysqldump 进程）+ `upload` 目录（附件等）+ `avatar` 目录（头像，位于 profile/avatar 而非 upload 下）+ `import` 目录（Excel 导入的图片文件）。`download` 目录（导出临时产物，可随时重新导出）**不纳入**。
- R3. 备份包为 zip 格式，内含清单文件（包格式版本号、应用 schema 版本、生成时间、表清单、文件目录统计），供还原时校验兼容性。备份范围声明：仅表结构与数据，不含视图/触发器/存储过程（当前库无此类对象）。
- R4. agent 提供备份命令（与界面按钮同一后端能力），agent 结果中返回备份包的下载路径或引导用户走界面下载。

**还原（上传还原）**

- R5. 界面提供"数据还原"入口：上传备份包 → 校验（清单格式、包格式与 schema 版本兼容——schema 不一致一律拒绝并提示所需应用版本，不做自动适配）→ 预览摘要（将还原 N 表 M 条记录、X 个文件，将替换当前全部数据；**单列 sys_user 变更明细——账号数与管理员凭据变更显式告警**）→ 用户二次确认 → 执行还原。解压防护：解压前逐条校验 zip 条目路径规范化后必须落在目标目录内（拒绝路径穿越），并设总解压大小与条目数上限，超限整体拒绝还原。
- R6. 还原语义为**全量替换**：现库全部表按包内结构重建后导入包内数据（表结构与数据均以备份包为准）；`upload`/`avatar`/`import` 目录内容替换为包内文件。还原过程单事务或可回滚，失败不得留下半状态。
- R7. 还原执行前自动生成"还原前快照"（当前数据的临时备份包），还原失败可回退；还原成功后快照按策略清理（保留最近 1 份即可）。已明示代价：仅保留最近一个恢复点意味着链式还原（连续多次还原）无法回到倒数第二次之前的状态，此类需求由服务器侧每日 dump 兜底（仅 DB 侧）。快照的存放位置与清理语义见 R10。
- R8. 还原成功后界面给出明确提示（成功+影响的记录/文件数）；**当包内 sys_user 含当前会话用户（按 userId 匹配）时不要求重新登录**，现有会话保持有效；否则提示重新登录。
- R9. 还原期间阻塞并发的其他写入操作（导入/agent 写操作），避免还原中途产生新数据丢失。

**安全**

- R10. 备份与还原端点均限管理员（沿用现有 userId==1 管理员判定先例），以方法级鉴权强制生效——现有安全配置 `/system/**` URL 层 permitAll，方法级注解是新端点的唯一 URL 内防线，实现不得只依赖 URL 层；还原作为 destructive 操作，操作记录进系统日志（@Log 审计）。备份包与还原前快照落盘于**不经 `/profile/**` 静态映射的专有目录**（`/profile/**` 当前匿名放行且直映射磁盘，落入即等于全库数据匿名可下载），再次取回仅能经鉴权端点；快照与临时包的清理策略须覆盖失败/中断的异常残留路径。

## Key Decisions

- **JDBC 逻辑导出/导入，不调 mysqldump 进程**——零外部依赖，Windows/Linux 通用，新机器还原不要求装 MySQL 客户端；全库规模（60 表、个位数 MB dump）下性能无虞。
- **还原前自动快照**——全量替换不可逆，快照是成本趋近零的后悔药（失败回退 + 误还原补救）。
- **手动触发，不做应用内定时备份**——服务器 cron 的每日 mysqldump 保留，职责不重叠；应用内定时+保留策略+磁盘管理是成倍的实现面，当前单用户场景收益低。
- **挂载现有"数据备份"按钮**——界面入口已存在（当前 404），补实端点即闭环，不新增导航结构。
- **Redis 数据不纳入备份**——token/验证码/配置缓存全部可再生（备份包数据导入后字典/参数缓存按需重建），AI 会话与 agent 审计均在 MySQL，已在全库备份范围内。

## Key Flows

- F1. 备份：用户点"数据备份" → 后端锁写入（见 R9 同机制）→ JDBC 导出全库 → 打包 zip（数据+文件+清单）→ **解锁** → 流式下载已生成的包文件（锁的必要性窗口仅覆盖导出/打包的一致性快照期，不覆盖传输期）。
  - **Covers:** R1, R2, R3, R9
- F2. 还原：用户上传备份包 → 校验与预览 → 二次确认 → 锁写入（R9 同机制）→ 生成还原前快照 → 全量替换（库+文件）→ 清除并重建字典/参数缓存 → 成功提示（或失败回退）→ 解锁。
  - **Covers:** R5, R6, R7, R8, R9

## Acceptance Examples

- AE1. 备份：点击按钮得到 zip；在全新 MySQL 实例 + 空 profile 目录的新环境上传该包还原后，笔记、多维表（含链接列）、附件图片、用户账号全部与备份时一致。
  - **Covers:** R2, R6
- AE2. 还原中途失败（如包损坏）：系统自动回退到还原前状态，数据与还原前完全一致，界面提示失败原因。
  - **Covers:** R6, R7
- AE3. 还原成功后：包内含当前会话用户时登录会话仍可用、无需重新登录；界面显示还原摘要。
  - **Covers:** R8

## Scope Boundaries

- 不做应用内定时备份、保留策略与磁盘占用管理（服务器 cron mysqldump 承担定期备份）。
- 不做合并式还原（追加/跳过主键冲突）；不提供包内部分内容选择性还原。
- 不做应用本体分发——新机器按部署手册装好应用后，用本功能还原数据。
- agent 侧仅提供触发备份与（视实现成本）触发还原的命令，不改变 agent 现有消息契约的文件下载能力。

## Dependencies / Assumptions

- **备份生成/下载侧**：全库 60 表 dump 个位数 MB、文件目录（upload+avatar+import）当前约 190MB/百级文件——在文件目录总量 ≤500MB 内单请求同步打包可行（边界条件，超出则需改造为异步任务）；超出即重估，不做提前的异步架构。
- **还原上传侧**：备份包约 190MB 级，现有 multipart 上限（max-file-size 10MB / max-request-size 20MB）无法承载单请求上传——还原通道须调高服务端 multipart 上限并配套 nginx `client_max_body_size` 与超时边界（部署手册 nginx 段同步更新），不做分片上传（当前体量下不必要）。
- 备份包格式版本化（清单内版本号），未来包结构演进时旧包仍可识别与拒绝。
- `download` 目录为可再生产物这一判断已确认（前端从不调用带 delete 的下载接口，导出临时文件仅即时用途）。
