# 雨滴笔记 AI 自然语言代理需求

## Summary

在 notepad 前端新增一个独立的 AI agent 面板，用户用自然语言描述操作意图（如"把当前笔记里所有提到项目A的段落都加个标签"、"新建一张客户表，列包含姓名/电话/公司"），LLM 解析意图后生成完整操作计划，用户确认后由 Java 后端直接调用雨滴笔记 Service 层执行。MVP 覆盖笔记与多维表子系统（dwtable/column/record，不含 block 与 notelink），破坏性操作在执行到该步骤时再次确认。

agent 复用现有 GLM AI 聊天基础设施（`ruoyi-system/.../ai/` 与 `notepad/src/views/aiChat/`），但作为独立面板存在，不与既有 AI 对话弹框耦合。

## Problem Frame

雨滴笔记的笔记与多维表功能分散在多个页面，且多维表的四子系统（表/列/记录/块）操作路径较深。用户在执行批量或跨实体操作时（如"给当前表加 3 列再填 5 条记录"、"把这条笔记移到另一个文件夹"）需要频繁切换界面、重复点击，效率低且易错。

已有 CLI（`cli/src/rainote/`）证明这些操作可以被结构化描述与批量执行，但 CLI 面向脚本与自动化场景，普通 Web 用户不会使用。本 agent 把 CLI 已验证的操作语义搬到 Web 前端，用自然语言作为入口，让用户在当前页面就近完成操作，无需离开上下文。

关键张力：LLM 生成操作有出错风险，且雨滴笔记后端无乐观锁（参见 `cli/README.md` 安全警告），因此 agent 必须在执行前展示完整计划并强制用户确认，破坏性步骤执行时再次确认，且所有操作必须有审计线索。

## Key Decisions

- **直接调用 Service 层而非 subprocess 调用 CLI** — CLI 是面向外部脚本与自动化的产物，agent 运行在 Java 后端进程内，复用已注入的 Service Bean 更快、更安全、事务一致；subprocess 调用 CLI 会引入进程管理、token 传递、stdout 解析等不必要的复杂度。CLI 的端点语义与命令结构作为 agent 操作能力的参考来源，而非运行时依赖。
- **先计划后执行** — LLM 一次性输出完整步骤列表（含每步的目标实体、操作类型、参数），前端渲染为可审阅的计划卡片，用户确认后才开始执行。禁止 LLM 边想边执行。这把 LLM 的不确定性限制在"计划生成"阶段，执行阶段是确定性的。⚠️ 本设计依赖 Spike 验证的 ≥80% 计划正确率门槛；若 Spike 未达标，R8-R14 须改为迭代式规划设计（多轮 UI、部分计划展示）。
- **破坏性步骤执行时再次确认** — 计划确认后，执行到破坏性步骤（删除、批量修改、不可逆操作）时前端暂停并弹出二次确认。计划级确认覆盖整体意图，步骤级确认覆盖不可逆动作。
- **伴随式上下文感知** — agent 面板感知当前页面上下文（当前笔记 ID、当前多维表 ID、当前选中的记录/列），作为 LLM 的隐式上下文。用户说"这张表"时 agent 知道指哪张表。上下文由前端注入，用户不需显式粘贴 ID。
- **MVP 排除 block 与 notelink** — block（笔记块）操作粒度细、与 EditorJS 耦合深，LLM 难以稳定生成；notelink（语义关联）涉及双链列与查找列的级联重算，风险高。两者留待后续迭代，MVP 聚焦笔记 CRUD + 多维表/列/记录的 CRUD 与批量操作。
- **独立面板而非嵌入现有 AI 对话弹框** — 现有 AI 对话（`notepad/src/views/aiChat/`）是通用聊天，无操作执行能力；agent 面板需要计划渲染、二次确认、执行进度等专用 UI。复用后端 GLM 调用与鉴权基础设施，但前端组件独立。
- **操作能力由后端声明，前端不自行构造** — 后端维护一份"agent 可执行操作清单"（操作名、参数 schema、是否破坏性、对应 Service 方法），LLM 的工具调用被约束在这份清单内。防止 LLM 编造不存在的操作。
- **自然语言入口而非命令面板** — 命令面板（Cmd+K 模糊搜索操作清单）能以更低成本交付批量操作的可发现性，且无 LLM 延迟与确认开销。但命令面板要求用户知道操作名并理解参数结构，无法处理"把当前笔记里所有提到项目A的段落都加个标签"这类需要语义理解的模糊意图。MVP 选择自然语言入口以覆盖意图理解场景，命令面板可作为后续迭代的补充入口（power user 快速执行已知操作）。
- **确认疲劳缓解** — 两层确认（计划级 + 破坏性步骤级）存在确认疲劳风险：用户在多次正确计划后机械点击，罕见错误计划也会被确认。MVP 通过按影响量级缩放确认摩擦缓解：单实体破坏性操作用点击确认；批量破坏性操作（影响超过 Thresholds 小节定义的阈值）须显著展示受影响实体数量并升级摩擦（如输入实体名称或数量确认）。
- **只读查询跳过计划确认** — 只读查询操作（操作类型=查询）无副作用，强制用户确认计划造成不必要摩擦。MVP 中查询操作由 LLM 直接生成并执行，结果展示在对话流中，不走 R12-R14 的计划卡片确认流程；仅创建/更新/删除操作走完整计划确认流程。

## Requirements

### 术语定义

- **破坏性操作** — 满足以下任一条件的操作：(a) 导致数据不可逆丢失（删除）；(b) 影响范围超出单一实体（级联删除，如删表连带删列删记录）；(c) 修改后无法通过审计日志还原原值（覆写更新且无历史版本）。单纯的创建操作非破坏性；更新操作默认非破坏性，除非涉及上述条件。
- **会话（session）** — 指 notepad 前端单次 SPA 加载周期，不刷新页面的情况下页面切换视为同一会话；刷新页面、关闭/重开标签页视为新会话。会话内对话历史保持在内存中，不跨会话持久化。
- **批量** — 计划层面的展开机制，非操作类型。用户意图中的批量请求（如"创建 5 条记录"）在计划生成时展开为 N 个同类单实体步骤，共享同一 `bulkGroupId`。现有 Service 层不支持批量插入/更新的单次调用。
- **当前选中** — 用户在多维表页面最近一次单选或多选的实体 ID 数组。多选时上下文以数组形式传递给 LLM；列的"选中"指用户最近聚焦的列。
- **显示名称** — 上下文展示用的实体可读标识：笔记取标题、多维表取表名、列取列名、记录取首个文本类型列的值（截断 20 字符，无文本列时显示"记录 #ID"）。

### 入口与界面

- R1. 在 notepad 侧边栏新增 agent 入口，点击后在主内容区右侧打开 agent 面板（与笔记/表格编辑区并排，非弹框）。
- R2. agent 面板布局：上方为对话消息流（用户输入 + agent 回复 + 计划卡片 + 执行结果），下方为输入框。
- R3. agent 面板可折叠/展开，折叠时不影响主内容区操作。
- R4. agent 面板状态在页面切换时保持（在同一个 notepad 会话内不丢失对话历史，"会话"定义见术语定义小节）。

### 上下文感知

- R5. 前端在每次发送用户消息时，附带当前页面上下文：当前笔记 ID（如在笔记编辑页）、当前多维表 ID（如在表格页）、当前选中的记录 ID/列 ID 数组（"当前选中"定义见术语定义小节，多选时以数组形式传递）。
- R6. 上下文以结构化字段传递给后端，后端将其作为 LLM 的 system prompt 的一部分。
- R7. 用户可在 agent 面板手动清除或修改自动注入的上下文。修改机制支持三种方式：(a) 上下文编辑器（展示当前实体类型与 ID，支持手动输入替换）、(b) 自然语言指令（如"我说的不是当前表，是上周那张"——由 LLM 解析为上下文变更请求，非操作意图）、(c) 历史实体选择器（从最近访问的实体列表中选择）。修改后影响后续所有消息，直到再次修改或清除。

### 意图解析与计划生成

- R8. 用户发送自然语言消息后，后端调用 LLM，LLM 输出一份操作计划（JSON 结构），包含有序步骤列表。
- R9. 每个步骤包含：步骤序号、操作名（来自后端操作清单）、目标实体类型（笔记/多维表/列/记录）、操作类型（查询/创建/更新/删除）、参数、是否破坏性（定义见术语定义小节）、人类可读描述、批量组 ID（可选，标识属于同类批量展开的步骤组，"批量"定义见术语定义小节）。用户意图中的批量请求在计划生成时展开为 N 个同类单实体步骤，共享同一 `bulkGroupId`——现有 Service 层仅支持单实体 CRUD + 按 ID 批量删除，不存在批量插入/更新的单次调用。计划超过阈值步数（见 Thresholds 小节）时须向用户提供汇总确认而非全量逐条渲染：默认展示分类汇总（创建 X 步、删除 Y 步、更新 Z 步），提供"展开明细"按钮逐条查看，破坏性步骤始终逐条展示不受汇总折叠。
- R10. LLM 的 system prompt 中包含完整操作清单，LLM 只能引用清单中声明的操作。若 LLM 输出的计划中包含清单外操作（如"导出 Excel"），后端校验阶段拒绝执行并返回错误，前端展示"agent 暂不支持该操作"。后端不会基于清单外操作构造 Service 调用。
- R11. 若 LLM 判断用户意图不明确或缺少必要参数，输出澄清问题而非计划，前端展示为 agent 的提问，用户回答后继续。

### 计划展示与确认

- R12. 前端将计划渲染为计划卡片：步骤列表，每步显示序号、操作描述、目标实体、是否破坏性标记（破坏性步骤用醒目颜色标注）。
- R13. 计划卡片底部提供"确认执行"与"取消"按钮。用户未确认前不执行任何步骤。
- R14. 用户可在确认前编辑计划：删除某步骤、调整步骤顺序、修改参数。操作类型（查询/创建/更新/删除）不可编辑——不可通过修改参数将创建操作变为删除操作。参数编辑采用三层校验链：(1) 前端实时校验（编辑时即时反馈 schema 约束违规）、(2) 确认时后端再次校验全部步骤参数、(3) 执行时 R16 兜底校验（防止前端绕过）。任一层失败即拒绝该参数并提示用户。参数编辑后后端重新评估该步骤的破坏性标记，若标记变化则更新计划卡片的破坏性标注（如更新操作的参数被改为删除标记字段，破坏性标记须同步升级）。
- R15. 计划确认后进入执行态，计划卡片变为执行进度视图：每步显示待执行/执行中/成功/失败/跳过/已阻塞状态。状态转换规则：`待执行 → 执行中 → 成功/失败/跳过`；当依赖步骤未成功完成时 `待执行 → 已阻塞`（R19）。已阻塞步骤不自动执行，须用户手动"级联跳过"或待依赖步骤重试成功后解除阻塞。
- R15a. agent 面板须在输入框上方显著展示当前激活上下文（实体类型、ID、显示名称，"显示名称"定义见术语定义小节），并在页面导航时实时更新，以便用户在发送前验证上下文与意图一致。防止用户从表 A 导航到表 B 后，agent 仍对表 A 操作。
- R15b. 用户可访问性基线：agent 面板须支持键盘导航（Tab/Enter/Esc 遍历计划卡片与确认按钮）、屏幕阅读器播报（执行进度变化时 ARIA live region 通知）、以及窄视口响应式（面板在 <768px 视口下折叠为底部抽屉而非侧边栏）。
- R15c. 执行态下用户可暂停执行并编辑未执行步骤（已执行步骤不可编辑）。可编辑操作：删除未执行步骤、调整未执行步骤顺序、修改未执行步骤参数（受 R14 三层校验链约束）。暂停期间不释放后端执行占位（R17a 多标签页锁仍持有），暂停后用户可选择"继续执行"或"取消剩余计划"。

### 执行与破坏性二次确认

- R16. 后端按计划顺序逐步执行，每步调用对应的 Service 方法。后端在执行每步前立即执行四层校验：(1) 操作名在清单内（R10）、(2) 参数符合 schema（R27，含用户编辑后兜底）、(3) 数据权限校验（R25）、(4) 前置条件校验（实体存在性、约束可用性）。任一层失败即中止该步并返回对应错误类型。当计划生成与执行间环境已变化（如实体已被删除）导致前置条件校验失败时，向用户展示"计划可能已陈旧"警告。
- R17. 执行到破坏性步骤时，前端暂停并弹出步骤级二次确认对话框，显示该步骤的完整描述与影响范围（含目标实体 ID 与受影响数量；受影响数量包含级联实体——如删表须实时查询并展示表下所有列与记录数），用户确认后才执行该步。升级摩擦触发条件有两个独立维度：(a) 计划中破坏性步骤数量超过阈值（见 Thresholds 小节），(b) 单步级联影响实体数超过阈值。任一维度超阈值即升级摩擦：显著展示受影响实体数量，用户须输入实体名称或数量确认。
- R17a. 并发策略：同一 agent 面板内执行期间用户发送的新消息进入排队状态（不阻塞输入），当前计划执行完成后依次处理排队消息，前端须显示排队消息数量。同一用户禁止在多个浏览器标签页同时打开 agent 面板并发执行计划（前端检测到多标签页时提示"agent 已在另一标签页打开"并禁用输入），避免无乐观锁环境下的并发冲突。
- R18. 用户在二次确认时可选择"跳过此步"或"取消剩余计划"（取消未执行步骤，不回滚已执行步骤）。跳过后触发 R19 依赖阻塞机制：若被跳过步骤有依赖步骤（如跳过建表后的建列），依赖步骤标记为"已阻塞"并提供"级联跳过依赖步骤"选项；无依赖关系的后续非破坏性步骤继续执行。
- R19. 依赖阻塞机制同时覆盖"失败"与"跳过"两种中断源：任一步骤未成功完成（失败或被跳过）时，前端显示失败原因（失败时）或跳过标记（跳过时），并提供"重试此步"（仅失败时可用）/"跳过此步"/"取消剩余计划"选项。不自动回滚已执行步骤（雨滴笔记无事务级回滚能力，回滚语义复杂，留给用户决策）。若未成功完成的步骤有依赖步骤（如建表失败或被跳过后的建列步骤），前端须标记依赖步骤为"已阻塞"并提供"级联跳过依赖步骤"选项，避免逐个失败产生混乱错误。
- R20. 每步执行结果实时反馈到计划卡片，全部完成后显示汇总（成功 N 步、失败 M 步、跳过 K 步）。
- R20a. LLM 调用失败或返回无法解析的输出时，前端显示"AI 暂时无法处理，请重试或换个说法"，输入框恢复可用，用户可重试或修改输入。不执行部分计划。LLM 调用参数：超时 30s、自动重试 2 次（指数退避：1s、3s）、重试期间前端显示"AI 思考中..."、部分计划已生成时全部丢弃不保留。
- R20b. 用户在执行期间刷新页面、关闭标签页或折叠面板时，当前执行中断且不可续传（后端无持久化执行状态，无法从中断点继续）。重新打开面板时显示"上次执行未完成"提示与审计日志链接，用户可查看已完成步骤。恢复路径为路径 A（不需 LLM 重解析）：用户可从审计记录中选择未完成的计划，前端展示原计划与已完成步骤状态，用户确认后后端直接执行剩余步骤（不重新调用 LLM），已执行步骤不重复执行。R19 的"重试此步"选项仅适用于执行期间面板保持打开的场景，刷新后不再可用。

### 审计与可观测

- R21. 后端为每次 agent 执行记录审计日志：用户 ID、时间、用户自然语言输入（经 R22 PII 脱敏后）、最终确认的计划、每步执行结果（成功/失败/跳过/已阻塞）、失败原因。审计记录写入时机：计划开始执行时创建审计记录（状态=执行中），每步状态变更时即时更新该记录，全部完成后标记状态=已完成。确保 R20b 刷新后可查询已完成步骤。
- R22. 审计日志持久化到数据库，按用户隔离，管理员可查询。审计日志须定义留存期限（90 天后自动归档/删除），对用户自然语言输入中的 PII 字段在持久化前做脱敏处理（手机号保留前 3 后 4、邮箱脱敏本地部分、身份证号保留前 6 后 4），管理员访问需基于角色权限键（非全部管理员可见全量原文）。
- R23. agent 面板内可查看当前会话内最近 N 条执行历史（N 值见 Thresholds 小节）。跨会话历史通过审计日志页面查询（R22），不在 agent 面板展示。

### 鉴权与安全

- R24. agent 复用 notepad 现有登录鉴权，未登录用户不可访问 agent 面板。
- R25. agent 执行的每个 Service 调用必须经过与 Web 前端直接操作相同的数据权限校验（如文件夹归属、多维表归属），不能因为"agent 发起的"就绕过校验。agent 直接调用 Service 层绕过了 Controller 的 @PreAuthorize RBAC 校验，因此 agent 必须在 Service 调用前显式执行等价的 RBAC 校验。权限键来源由操作清单声明（每个操作绑定一个权限键字符串），agent 运行时基于当前用户角色与权限键执行校验。⚠️ 本需求的前提（现有 Service 层具备数据权限校验能力）尚未验证——代码核实显示 MVP 范围内 NoteRecordController/NoteColumnController/NoteDwtableController 的 @PreAuthorize 几乎全被注释、NoteRecordServiceImpl 无 userId/归属校验，参见 Open Questions 第1条。该前提的解决方式已决策为两者并行（见 Open Questions 第1条 C1 决策，经 C3 核查修正）：归属根为 `note_note.auth` 字段（所属用户id）。agent 自建 `AgentOwnershipChecker` 通过层级链遍历校验归属——笔记操作直接校验 `note_note.auth`；多维表操作校验 `note_dwtable.noteId → note_note.auth`；列操作校验 `note_column.dwtableId → note_dwtable.noteId → note_note.auth`；记录操作校验 `note_record.dwtableId → note_dwtable.noteId → note_note.auth`。所有实体归属最终通过 note_note.auth 判断。同步加固 Service 层（含 NoteNoteServiceImpl）恢复 @PreAuthorize/ownership 检查。后续迭代为 dwtable/column/record 表补冗余归属列以消除层级链跳转开销。agent 自身的 R21 审计必须独立记录每步的实体 ID、操作类型与权限校验结果，不依赖后端 @Log（已知存在盲点）。
- R26. 后端操作清单中的破坏性操作必须显式标记，前端据此触发二次确认；标记与 Service 方法的实际破坏性必须一致，由后端清单声明而非 LLM 判断。
- R27. 用户输入与经 Service 读取回的实体元数据均为不可信输入（LLM 攻击面）。MVP 范围内 agent 不读取笔记正文/记录正文字段值传给 LLM；R27 所指"经 Service 读取回的内容"仅限实体元数据（ID、标题、表名、列名等显示名称），用于计划生成时的上下文增强，不包含正文内容。后端对 LLM 生成的每步参数强制按操作清单 schema 校验后再渲染计划卡片；用户编辑参数后须按 R14 三层校验链再次校验。破坏性步骤的二次确认对话框必须回显完整参数（含目标实体 ID）供用户核对，防止参数级提示注入误导用户批准删除错误实体。
- R28. **安全前置条件（止血方案）**：agent 上线前必须完成现有 Note* 子系统的安全止血加固：(1) SecurityConfig（`ruoyi-framework/.../config/SecurityConfig.java:122`）移除 `GET /system/note/**` 匿名放行，恢复登录鉴权；(2) **仅恢复破坏性端点**（remove/update/removeAll/clearGarbage/deduplicate 等）的 @PreAuthorize 注解，权限键命名 `system:note:remove`/`system:note:edit`，sys_menu 同步添加权限项并分配给现有角色；查询/创建端点暂不动以避免破坏现有前端列表加载（C4 决策）。本需求采用止血方案：破坏性 GET 端点（remove/removeAll/removeAllData/clearGarbage/cancelCollection/collectionNote/setTemplate/removeTemplate/deduplicate 等 12 个）暂保留 HTTP 方法不改 POST/DELETE，避免破坏现有 notepad 前端调用。此为遗留 REST 语义风险——GET 删除违反 REST 安全语义，仍可被 CSRF/爬虫在已登录会话下触发，须在后续迭代中改为 POST/DELETE（见 Scope Boundaries）。agent 路径不依赖 Controller 的 @PreAuthorize（agent 自建 AgentOwnershipChecker，见 R25/C1），但 Web 前端路径的安全性依赖此前置加固。⚠️ 未完成 R28 前不得上线 agent。

## Key Flows

- F1. 单步查询操作
  - **Trigger:** 用户在多维表页面打开 agent，输入"这张表有多少条记录"。
  - **Actors:** 用户、agent 前端、agent 后端、LLM、NoteRecordService。
  - **Steps:** 前端附带当前多维表 ID 作为上下文 → 后端调用 LLM 解析意图 → LLM 输出单步查询计划（操作名=记录计数，参数=当前表 ID，非破坏性）→ 前端渲染计划卡片 → 用户确认 → 后端调用 NoteRecordService 查询 → 返回数量 → 前端在对话流中展示结果。
  - **Outcome:** 用户得到记录数量，无数据变更。
  - **Covers:** R5, R8, R9, R12, R13, R16, R20.

- F2. 多步创建操作（含破坏性二次确认）
  - **Trigger:** 用户输入"新建一张客户表，列包含姓名/电话/公司，再删掉旧的那张测试表"。
  - **Actors:** 用户、agent 前后端、LLM、NoteDwtableService、NoteColumnService、审计日志。
  - **Steps:** LLM 输出 5 步计划：① 创建多维表（操作类型=创建，非破坏性）② 创建姓名列（操作类型=创建，非破坏性，bulkGroupId=col-batch-1）③ 创建电话列（操作类型=创建，非破坏性，bulkGroupId=col-batch-1）④ 创建公司列（操作类型=创建，非破坏性，bulkGroupId=col-batch-1）⑤ 删除旧测试表（操作类型=删除，破坏性）→ 用户确认整体计划 → 逐步执行 ①-④ → 执行到 ⑤ 时前端暂停弹出二次确认 → 用户确认删除 → 执行 ⑤ → 全部完成 → 审计日志记录全部步骤。
  - **Outcome:** 新表与 3 列创建成功，旧表删除成功，审计完整。
  - **Covers:** R9, R12, R13, R16, R17, R18, R20, R21.

- F3. 意图不明确触发澄清
  - **Trigger:** 用户输入"把这些都改一下"。
  - **Actors:** 用户、agent 前后端、LLM。
  - **Steps:** LLM 无法确定"这些"指什么（无选中记录）与"改一下"改什么 → LLM 输出澄清问题"你指的是当前选中的哪些记录？想改成什么？" → 前端展示为 agent 提问 → 用户回答"选中的 3 条记录，状态改成已完成" → LLM 重新生成计划。
  - **Outcome:** 用户补充信息后计划生成成功。
  - **Covers:** R11.

- F4. 执行失败处理
  - **Trigger:** 计划执行中某步因唯一约束冲突失败。
  - **Actors:** 用户、agent 前后端、Service 层。
  - **Steps:** 第 2 步创建列失败（列名重复）→ 后端返回错误 → 前端标记第 2 步失败并显示原因 → 前端提供"重试/跳过/取消剩余"选项 → 用户选择"跳过" → R19 依赖阻塞检查：第 3 步（创建另一列）与第 2 步无依赖关系，继续执行第 3 步 → 完成。
  - **Outcome:** 部分步骤成功，用户知情并决策，审计记录跳过与失败。
  - **Covers:** R18, R19, R20, R21.

## Acceptance Examples

- AE1. 上下文感知免粘贴 ID
  - **Given:** 用户在多维表 ID=42 的页面打开 agent。
  - **When:** 用户输入"给这张表加一列叫'优先级'"。
  - **Then:** LLM 生成的计划中"创建列"步骤的 tableId 参数=42，用户无需手动输入 ID。计划卡片显示"在当前表（ID=42）创建列：优先级"。

- AE2. 破坏性步骤二次确认
  - **Given:** 计划包含 3 步：① 更新记录（非破坏性）② 删除记录（破坏性）③ 创建记录（非破坏性），用户已确认整体计划。
  - **When:** 执行到第 2 步。
  - **Then:** 前端暂停，弹出二次确认对话框显示"即将删除记录 ID=5，此操作不可逆"，提供"确认删除/跳过/取消剩余计划"。用户未选择前第 2 步不执行，第 3 步也不执行。

- AE3. 操作清单外请求被拒
  - **Given:** 用户输入"把这张表导出成 Excel"。
  - **When:** LLM 在 system prompt 中已知操作清单，解析意图后输出包含"导出 Excel"操作的计划，后端校验阶段发现该操作不在清单中。
  - **Then:** 后端拒绝执行并返回错误，前端展示"agent 暂不支持导出 Excel 操作"。用户不会被引导到不存在的功能。

- AE4. 数据权限校验不绕过
  - **Given:** 用户 A 无权访问多维表 ID=100（属于用户 B）。
  - **When:** 用户 A 通过 agent 输入"删除表 ID=100"。
  - **Then:** 即使用户 A 确认了计划，后端执行删除时 agent 的 RBAC 校验（R25，基于操作清单声明的权限键）失败，返回 403，前端标记该步失败并显示"无权操作此表"。⚠️ 本示例依赖 R25 前提（agent 自建 RBAC 或现有 Service 已加固），参见 Open Questions 第1条。

- AE5. 审计日志完整性
  - **Given:** 用户执行了一次包含 4 步的计划，其中第 3 步失败、第 4 步跳过。
  - **When:** 执行完成后。
  - **Then:** 审计日志记录：用户 ID、时间戳、用户自然语言输入（经 R22 PII 脱敏后）、完整计划 JSON、4 步的状态（成功/成功/失败/跳过）、失败步骤的错误信息。管理员可在审计页面查询到此条记录。

- AE6. 批量操作效率优势
  - **Given:** 用户想在多维表中添加 5 列（姓名/电话/邮箱/公司/职位）并填入 3 条记录。
  - **When:** 用户通过 agent 输入"在这张表加 5 列：姓名、电话、邮箱、公司、职位，再填 3 条记录：张三/13800000000/zs@a.com/A公司/工程师，李四/..."。
  - **Then:** agent 生成 8 步计划（5 创建列 + 3 创建记录），用户一次性确认后批量执行。相比 manual 操作（5 次加列点击 + 3 次记录填写 = 至少 8 次界面交互），agent 将交互降为 1 次确认。

## Success Metrics

MVP 上线后须度量以下指标以验证 agent 是否真正解决所述问题：

- **效率指标**：agent vs 现有 UI 完成同一批量操作的中位用户步骤数（目标：agent 步骤数 < manual 步骤数的 50%）
- **错误指标**：计划确认拒绝率（用户看到计划后取消的比例，反映 LLM 计划质量）与执行后修正率（执行完成后用户立即手动修正的比例，反映计划正确性）
- **采用指标**：DAU 中使用 agent 的比例与人均使用次数（反映 agent 是否真正比 manual 更高效）

## Spike / Pre-implementation Validation

在全面实现前，须先验证以下关键假设：

- **LLM 一次性计划生成能力验证** — 用目标 GLM 模型运行 20+ 条样本输入（覆盖 F1-F4 复杂度，含 5 步以上跨实体计划），测量计划正确率（无需用户修正的计划比例）。全面实现门槛：≥80% 的计划无需用户修正。若低于门槛，须重新设计为迭代式规划（多轮 UI、部分计划展示）。
- **LLM 结构化 JSON 输出可靠性验证** — 测量 GLM 在 system prompt 约束下的 JSON 解析失败率。若失败率 >5%，须评估结构化输出技术（function calling、JSON mode）或增加重试与 schema 校验层。

## Scope Boundaries

### Deferred for later

- **block（笔记块）操作** — EditorJS 块粒度操作与 LLM 生成的不确定性冲突大，留待后续迭代。
- **notelink（语义关联）操作** — 涉及双链列与查找列的级联重算，风险高，留待后续迭代。
- **跨表语义关联与查找列重算** — 依赖 notelink，同样延后。
- **基于字段值条件筛选的批量操作** — 如"把所有状态为'已完成'的记录改成'已归档'"或"删除所有创建于上个月的记录"。此类操作需要 LLM 先按条件查询记录集合再生成批量修改/删除计划，但 MVP 的 GLM 信任边界（见 Dependencies）规定不传递记录数据本体给 LLM，且 Service 层不支持条件批量 UPDATE/DELETE 的单次调用。MVP 仅支持用户显式指定目标实体 ID 的批量操作（如"删除记录 1、2、3"），LLM 不自行基于字段值筛选并生成批量操作计划。后续迭代可考虑引入"查询步骤返回 ID 列表给 LLM"的受控路径以支持此场景。
- **计划回滚** — 雨滴笔记后端无事务级回滚能力，MVP 只支持失败时跳过/取消，不自动回滚已执行步骤。
- **dwtable/column/record 表补冗余归属列** — 当前这 3 张表无直接归属字段，agent 归属校验通过层级链跳转到 `note_note.auth` 实现（C1 决策，归属根为 note_note.auth）。后续迭代为这 3 张表补冗余归属列（如 auth/createBy）后可简化 `AgentOwnershipChecker`，消除层级链遍历的多次 DB 查询开销。
- **破坏性 GET 端点改 POST/DELETE** — 现有 12 个破坏性/状态变更端点走 GET 方法（含 removeAllData 可清空全库，C2/R28 止血方案仅恢复鉴权不改方法）。后续迭代须改为 POST/DELETE 以符合 REST 安全语义，消除已登录会话下的 CSRF/爬虫触发风险。须同步修改 notepad 前端 axios 调用。
- **多模型选择** — MVP 复用现有 GLM 集成，不引入模型选择器。
- **agent 主动建议** — MVP 只响应用户主动输入，不主动观察用户操作并提供建议。
- **流式计划生成** — MVP 等待 LLM 输出完整计划后再展示，不做打字机式逐步展示。

### 优先级分层与 a/b 编号说明

文档中 R1-R27 为主编号需求，R15a/R15b/R17a/R20a/R20b 为 ce-doc-review 后追加的补充需求（a/b 后缀编号）。MVP 归属如下：

- **MVP 必需（P0）**：R1-R14、R15、R15a、R16-R20、R20a、R20b、R21、R24-R27 — 核心流程、上下文感知、执行与错误处理、审计与安全
- **MVP 重要（P1）**：R15b（可访问性基线）、R22（审计留存与 PII 脱敏）、R23（会话内执行历史） — MVP 可降级但不缺失
- **后续迭代（P2）**：无 — 所有 a/b 补充需求均属于 MVP 范围

完整的 P0/P1/P2 分层（含 R1-R27 每条）仍需用户确认，参见 Open Questions 第3条。

### Outside this product's identity

- **完全自主的定时任务 agent** — agent 是用户驱动的伴随式助手，不是后台自动执行 agent。
- **跨用户协作** — agent 只操作当前登录用户有权访问的数据，不涉及跨用户协作语义。
- **外部系统集成** — agent 不调用雨滴笔记以外的系统（如发邮件、调外部 API）。

## Dependencies / Assumptions

- 现有 GLM AI 聊天后端基础设施（`ruoyi-system/.../ai/`）可复用，API Key 与模型配置已就绪。但现有 IAiChatService.chat() 绑定 AiChatSession 持久化、无 system prompt 参数、流式输出纯文本而非结构化 JSON；agent 的计划生成路径无法直接复用 chat()，需新建一个复用 GlmConfig 的 GLM 调用方法。
- **GLM 第三方信任边界**：传递给 GLM 的数据范围限于用户输入文本 + 结构化上下文 ID（笔记 ID、多维表 ID、记录/列 ID）。不传递笔记正文/记录数据本体（仅传 ID 与 schema）。查询操作的返回结果中，记录 ID 列表可传递给 LLM 用于后续步骤的目标实体指定（如用户先查询再批量操作的受控路径），但记录正文字段值（如文本内容、数值、日期）不传递。GLM 调用失败时不在错误信息中回显敏感上下文。用户输入可能含 PII，须遵循最小必要原则。
- CLI 端点清单（`cli/src/rainote/client/endpoints.py`）与命令实现（`cli/src/rainote/commands/`）作为 agent 操作能力清单的参考来源，但 agent 运行时不依赖 CLI 进程。
- 雨滴笔记后端 Service 层（NoteNoteService、NoteDwtableService、NoteColumnService、NoteRecordService）已具备 MVP 所需的单实体 CRUD 方法与按 ID 批量删除方法，agent 直接调用。批量创建/更新在计划生成时展开为 N 个单实体步骤。agent 计划的每步 Service 调用为独立事务，一步失败不回滚已提交步骤，与 R19 的"不自动回滚"语义一致。
- 后端无乐观锁，agent 与 Web 前端直接操作并发时遵循"最后写入者胜出"语义，agent 不额外解决并发冲突（与 CLI 一致，参见 `cli/README.md`）。CLI README 确认 revisionId 硬编码为 1L，--check-revision 提供虚假保护，agent 继承此语义。
- LLM 输出格式可通过 system prompt 约束为结构化 JSON，后端解析失败时返回错误而非执行部分计划。解析失败率须在 Spike 阶段验证。
- **多维表与笔记的归属关系**：多维表（dwtable）独立于笔记存在，不嵌套于某个笔记下。因此表格页时"当前笔记 ID"为 null，不注入所属笔记上下文；笔记页时"当前多维表 ID"为 null。跨实体操作（如"把这条笔记的内容填到那张表里"）需要用户在 R7 上下文编辑器中显式指定目标实体 ID，agent 不自动跨页推断归属。
- **Note* 子系统安全加固前置（R28）**：现有 SecurityConfig 对 `GET /system/note/**` 匿名放行 + 破坏性操作走 GET + @PreAuthorize 全被注释，存在匿名删库漏洞（removeAllData 可匿名清空全库）。agent 上线前须完成止血加固（移除匿名放行 + 恢复 @PreAuthorize），破坏性 GET 改 POST/DELETE 留待后续迭代。agent 路径自建 AgentOwnershipChecker 不依赖 Controller 加固，但 Web 前端路径的安全性依赖此前置。
